# Maintain the design package

`design/` is the living picture of what this repo actually deploys: how many
jobs, pipelines, tables and views the estate has and how they connect. It used
to be hand-edited draw.io XML, and it rotted the way hand-edited diagrams do:
arrows with no waypoints ran straight through cards, labels clipped, every new
domain was bolted on as another strip at the bottom. So the diagrams are now
**generated from the estate**, laid out through the vendored
**drawio-architecture-designer** kit, and audited before they are written.

## What is generated, what you edit

| Part | File(s) | How it changes |
|---|---|---|
| **Implementation map** | `design/02_implementation_end_to_end.drawio` | GENERATED by `scripts/design_diagram.py`: page 1 estate overview (domains, pipelines, jobs + an inventory table), one lineage page per domain (sources, layers, quarantine, orchestration, edge jobs, consumers), last page delivery (CI/CD triggers to bundle targets). Never hand-edit. |
| **Conceptual design spec** | `design/01_design_config_driven_medallion.drawio` | GENERATED by `scripts/design_spec.py` (Context, Author, Generate, Run, Ship). Edit the TEXT in that script when the design intent changes. |
| **Overlay** | `design/estate.yml` | EDIT: what no bundle YAML states - upstream source systems, downstream consumers, what an edge job reads and writes. |
| **Images** | `design/images/*.png` | GENERATED by `make design` (draw.io Desktop CLI, else the kit's HTML twin). Never hand-edit. |
| **Pipeline inventory** | `design/PIPELINES.md` | GENERATED from `config/` by `scripts/design_inventory.py`. Never hand-edit. |
| **Customer overview** | `design/OVERVIEW.md` | EDIT: customer-facing narrative that embeds the images. Refresh when the story changes. |

The estate facts come from the files that define them and nothing else:
`config/` artifacts (tables, views, sources, lookups, quality gates,
quarantine), `resources/*.yml` (pipelines, jobs, triggers, task kinds),
`targets/*.yml` + `.github/workflows/ci-cd.yml` + the `Makefile` help (the
delivery page), and `design/estate.yml`. If a fact is not in one of those, it is
not on the diagram - add it to the overlay rather than to the picture.

## Enforcement (why hand edits fail)

- **Agent hook**: `.cursor/hooks/design_drawio_guard.py` (wired for Claude Code,
  Codex and Cursor) denies any write to `design/*.drawio` or
  `design/images/*.png` - an Edit/Write tool call or a shell `sed -i`, redirect,
  `tee`, `cp`/`mv` onto one.
- **CI + pre-commit**: `make check-design` regenerates PIPELINES.md and both
  diagrams in memory and fails if the committed files differ (stale or
  hand-edited) or if the layout audit finds anything: text overflowing its card
  (height or an unbreakable token too wide), non-black text, colliding cards, an
  arrow crossing a card it does not connect, or two unrelated arrows drawn on
  top of each other.

## When to invoke

YES - in the same PR/work session as any of:

- A new, renamed or removed config artifact (table, view, sink) or a changed
  source, lookup, target kind, CDC setting or quality gate.
- A new, renamed or removed pipeline or job under `resources/*.yml`, or a
  changed trigger/schedule or task kind.
- A new target, or a changed CI/CD trigger in `.github/workflows/ci-cd.yml`.
- A new upstream source system, downstream consumer, or edge-job read/write
  (edit `design/estate.yml`).
- A request to change how the diagrams look or what they show (edit the
  generator - follow the **drawio-architecture-designer** skill).
- A change to the design intent (edit the text in `scripts/design_spec.py`).

NO - skip for pure internal refactors that change no file the generator reads.
When unsure, run `make check-design`: it tells you.

## Workflow

### 1. Regenerate

```bash
make design            # PIPELINES.md + both .drawio + design/images/*.png
```

For most estate changes this is the whole job: the generator picks up the new
table, job or pipeline, re-lays out the page, re-routes every arrow through the
gutters, and re-runs the audit. If the audit is not clean it prints the
findings and writes nothing - fix the cause (usually a label the generator
should shorten, or a layout rule in the generator), never the XML.

### 2. Declare what the code cannot say

Add or change `design/estate.yml` when a relationship is real but lives
outside the bundle:

```yaml
sources:        # upstream systems feeding a table (drawn in the Sources column)
  - {name: SAP S/4HANA, detail: CDS extracts via landing, feeds: [<domain>.bronze.<table>]}
consumers:      # downstream readers (drawn in the Serving column)
  - {name: Power BI, logo: dashboards, reads: [<domain>.gold.<table>]}
jobs:           # what an edge job reads / writes (its YAML only names schemas)
  <job_key>: {reads: [<domain>.<layer>.<table>], writes: "<where the output lands>"}
```

References are `<domain>.<layer>.<table>` (quarantine tables too); an unknown
one fails the generator. Only state what is true - an arrow is a claim that A
feeds B.

### 3. Look at it

```bash
make design-preview    # HTML twin + one PNG per page in .design-preview/ (gitignored)
```

Open the PNGs and read them the way a client would: every card legible, every
arrow leaving one card and landing on another, nothing floating. The audit
finds size mistakes; only looking finds ugly.

### 4. Changing the generator or the spec layout

Any edit to `scripts/design_diagram.py`, `scripts/design_spec.py` or
`scripts/drawio_kit/` follows the **drawio-architecture-designer** skill
(`.agents/skills/drawio-architecture-designer/SKILL.md`): one layout model,
shape-to-shape arrows with explicit waypoints in gutters (one lane per target,
buses for many-to-one, corridors for skipped columns), all text `#000000`
except white on dark fills, Page View off, Unity Catalog only from the bundled
official asset. Run `make design-preview` and read every page before
committing. Keep the generator deterministic - the same estate must always
produce byte-identical XML, or `check-design` becomes noise.

### 5. Refresh the customer overview

If the change alters the story a customer reads - a new capability, a changed
layer behaviour, a new source or consumer - update the matching prose in
`design/OVERVIEW.md` (it embeds `images/01_*` and `images/02_*`, so the
regenerated images flow through automatically). A structural change the
generator already drew needs no `OVERVIEW.md` edit.

### 6. Cross-check AGENTS.md and docs

Scan AGENTS.md's "Architecture" and "Codebase layout" sections (and the relevant
`docs/`). If the change also affects those, update them in the same PR.
Framework behavior itself is documented in the framework repo's
`docs/FRAMEWORK.md` - change it there, not here.

## Anti-patterns

- Editing `design/*.drawio` XML (by hand, with `sed`, or by opening it in
  draw.io and saving) - the hook denies it and `check-design` fails CI. The next
  `make design` would overwrite it anyway.
- Hand-editing a PNG or `design/PIPELINES.md` instead of regenerating.
- Hand-editing the standalone HTML instead of regenerating it. <!-- adopter-if:template -->
- Committing a changed estate without `make design` (CI fails on the drift).
- Putting a relationship on the diagram that no file states - declare it in
  `design/estate.yml`, or leave it off.
- A write-edge from a job/notebook INTO an SDP-owned table - violates the
  single-writer invariant; edge jobs READ pipeline tables (dashed) and write
  their own outputs (a line on the job card).
- Weakening the audit (skipping a finding class, loosening a tolerance) to get
  a layout through - fix the layout.

## Done check

1. `make design` ran; `design/*.drawio`, `design/images/*.png` and
   `design/PIPELINES.md` are staged with the change that caused them.
2. `make check-design` passes (current, not hand-edited, audit clean).
3. You looked at `make design-preview` output for every page you changed.
4. `design/estate.yml` states only true relationships; every reference resolves.
5. `design/OVERVIEW.md` still reads true (updated if the narrative changed).
   <!-- adopter-if:template start -->
   The standalone HTML is flagged in the PR if it needs regenerating.
   <!-- adopter-if:template end -->
6. The change is described in AGENTS.md in the same PR when the architecture
   moved.
